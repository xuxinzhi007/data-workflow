# 停下问

## 推荐先做哪个

**查询与推进挤在同一条路径。**

一句为什么：它已经在写盘，而且会跳过 G7；钩子和用例都还当 next 是只读的。

## 什么时候不该做

如果把「写完 decision.md 再跑 next，直接进入编码步骤」当成现在就要保留的使用方式，就不要先把自动推进删掉。那种情况下，该先决定钩子如何只读地发现未完成运行，再改推进路径。未拍板之前，不改业务代码。

另外三个候选都可以稍后展开：配置查找的分叉已经能实跑出来，但要先约定优先级；产物落点影响本工作流的机器门，若决定「评审产物本来就该落 docs/reviews/」，再加深才有意义；写入放行只在受保护路径遇上 change 时发作。

## 待拍板的架构选择

1. next 在文档阶段产物齐时自动推进，是预期的使用方式，还是只读查询上的泄漏？若是预期，钩子就不能再走同一条路径。
2. architecture-review 的产物根，以 JSON 声明的 `$REPO/docs/reviews/` 为准，还是与其它工作流一样落 `specs/<feature>/`？
3. change 要放行受保护路径时，是否继续借用 feature 的 plan.md / gate，还是按 change 自己的产物来判？
4. `gate_strict` 与 `protected_paths` 的文件查找顺序以谁为准（仓库根优先，还是工具目录优先；要不要包含 `.qoder` / `.agents` / `.claude` / `.codex` 和 `~/.config`）？
5. 第四个运行终态如果以后要加，判定是否必须收进与 hook 共用的一处？
