> 格式：**正方**主张要改，**反方**主张别动。每方只用可核对的证据（`文件:符号`、行数、命令）。
> 结论不取平均，按"哪方在具体论点上站得住"分项判。

## 议题一：项目该不该调整？

### 正方：该调，因为有一处结论写错了，且写错的方向对自己有利

**论据（最硬的一条）：**

`docs/competitive.md` 把"hook 坏了自己的降级策略"列在 **"真的差异点"** 一栏，写着"同类技能包里我没有找到对应设计（推断：多数技能包不管 hook 层）"。

官方 `hooks.md` 现在是这个：

> The action goes ahead, except for hooks whose failure blocks the action, for example a hook with `onFailure` set to `"block"`.

**同一套设计，官方有标准实现。** 那个"推断"是错的。

**为什么这条足以启动一次调整，而不是"以后再说"**：

1. `competitive.md` 开头自己写了：「过期后就按 `docs/agent-pain.md` 的说法——过期后要漏得响」。**这是项目自己定的规矩，现在漏了。**
2. 这不是口味问题，是**事实错误**，且错在"我比别人多了个东西"这种最容易自欺的方向上。
3. `claim-register.md` 整份文件存在的理由，原文是「有一批断言的证据强度和外部查不到出处的数字完全一样，但它们以陈述句进了架构论证」——**这次就是同一类事，只是发生在 `competitive.md` 而不是架构文档里。**

第二条（次硬）：**多 agent 那格也是反的。**

`competitive.md` 把"多 agent 编排纪律"列为 `●` 差异点，理由是本项目"取证可并行、裁决不可并行"。但官方口径是并行**可行**，靠 `isolation: worktree` 换隔离。本项目的"禁止并行"是**没有隔离手段的降级**，不是更严谨。

把降级写成优势，是 `scope.md` 那句"代理自己说这是小改动不算数"的镜像——**自己说这是优势，也不算数。**

### 反方：先别调，数字说明不了什么

**论据一：74 个 md / 4322 行脚本对一个技能包来说不少，但这是"证据链"的固有成本。**

`check_runner.py` 1851 行、43 个用例，`verify.sh` 跑一遍就覆盖五种检查入口、pnpm/yarn/pytest/cargo、拍板回复、读写区分、fail-open、UTF-8、跨仓库安装。**这些都是 `docs/agent-pain.md` 说的"红灯/命令输出"那一类真问题，不是自嗨。**

要砍，砍哪一行？砍掉一个用例，就是砍掉一条回归。

**论据二：`competitive.md` 那两格写错，改两行字就行，不需要"调整"。**

叫成"调整"会触发一次 `change`，`change` 有 6 条字面量门。**为了改两行字，先写 `decision.md` 六件事、再改文件、再写 `check.md`——这正是过度设计的现场。**

### 判定：正方赢，但赢得比它自己主张的小

- **该调**：`competitive.md` 两格是事实错误，且方向是对自己有利，必须改。**这一条正方站得住。**
- **不该叫"调整"**：反方对"为一个文字修正启动完整 change 流程"的批评是对的。这恰恰暴露了议题三的问题。

**净结论：调，但按最小动作调——改文档，不启动流程。**

## 议题二：为什么调？提升点在哪？

### 正方：三个提升点，按"能不能自证"排序

**① 证据分级要覆盖自己对自己的评价（当前最大漏洞）**

`scope.md` 定义了四态：已证实 / 推断 / 待确认 / 存在冲突，管的是**业务事实**。

但 `competitive.md` 是**对自己能力的评价**，这个评价**不受这套分级约束**——它用的是 `●/◐/○` 三个符号，没有"我这条是推断还是已证实"的强制字段。于是"同类里没找到（推断）"和"已证实"在表里长得一样（都是 `●`）。

**这是结构性漏洞，不是笔误。** 修法很轻：`competitive.md` 每格标证据强度，`?` 已经有了（"不是我判断它不行，是没有证据"），**把 `?` 的做法推广到所有格子**即可，不需要新机制。

**② 尺寸没有上限（真缺口）**

- `SKILL.md` 102 行
- `stages/` 24 个文件，1090 行
- 单文件最大 `requirement-analysis/SKILL.md` 161 行

官方 `skills.md`：技能正文压缩后重挂，**每技能 5000 tokens、总计 25000**，超了从最老的丢；`description` 截断 **1536 字符**。

本项目**不知道自己在这些预算里的位置**。这不是"能不能实现"的问题（实现不了，宿主行为），是"连量都没测"的问题。

**修法极轻**：`verify.sh` 加一条尺寸检查。不改架构，只把"超了会失效"变成一条跑得起来的断言。

**③ `claim-register.md` 有一条可以升格**

那条待确认的"同时只有 1 个 stage 在上下文"，官方 `skills.md` 证实了：技能正文作为一条 message 常驻、后续 turn 不重读。

**这条升格是免费的**——不涉及代码，只是把一条错的质疑改成对的机制描述。

### 反方：三个提升点里，只有第一个是真的必须

**① 同意。** 但要说清代价：`competitive.md` 现在**每一格**都要标证据强度，工作量从 2 格变成 20 行。而这 20 行里大部分是 `●` 已证实（`verify.sh` 可复核），**边际收益在递减**。

**② 反对，理由是本项目自己写的反过度设计。**

`scope.md`：「已有能力能满足时，复用。不为局部需求加新抽象、中间层、配置系统。」

尺寸检查加在 `verify.sh` 里，需要：定 N 和 M 两个数字、写检查逻辑、加回归用例。**而 N 和 M 是多少，本项目没有依据**——官方给的是 token 数，本项目数的是行数和字符数，**换算不了**。

**定一个拍脑袋的 N/M，就是新造一个"没有出处的数字"。** `claim-register.md` 那份"外部数字（未核实，不得当依据）"清单，写的正是这件事。

**③ 同意升格，但顺带指出**：升格后那条断言要跟着改措辞，否则会出现"登记表说已证实，competitive 还写着不成立"的新冲突。

### 判定：正方赢 ①③，反方赢 ②，且反方赢的方式很漂亮

- **① 该做**，但按反方的量级做：**只改事实错误的那几格，不做全表打分。**
- **② 不做**。反方的攻击正中要害：**没有出处的 N/M 就是新造一个假确定感**。要做也得先有依据（比如真去量一次 description 多少字符、在哪个宿主超了），**那是调研，不是改代码。**
- **③ 该做**，且要连带改 `competitive.md` 措辞。

## 议题三：是不是已经过度了？

这是最值得吵的一题，正反双方都有硬论据。

### 反方（主张"已经过度"）：三条

**论据一：`change` 有 6 条字面量门，而它自己的文件承认门不管质量。**

`workflows/change.json` 的 `requires`：原话、我理解你要的是、可能理解错、本质、怎样算满足、未知。六条。

`change.md` 自己写：

> 门只检查「有没有写」，不检查「写得好不好」。这是故意的…字面量门能拦住「没想就往下走」，拦不住「写了句废话」。

**那段话诚实，但也承认了：这 6 条门的产出，可以是一份填满废话的 `decision.md`。** 代价是每次 L1 小改都要写六行。

`change.md` 紧接着写：

> 不清楚时最优动作是 wait（问人），不是先编一个完整方案。但清楚的、小的、可逆的改动，也应该一口气做完——加门不是把每件事都变成问答。

**这句是在给自己打补丁。** 一个设计需要专门写一段"我不是要你每次都问答"，说明它确实造成了这个负担。

**论据二：1851 行 `check_runner.py` 是 43 个用例的自证实。**

这 43 个用例在验证什么？验证 `workflow_next.py` 的判定逻辑、hook 的拦截、门禁的 fail-open。

**它们验证的是门自己对不对，不是"这个改动对不对"。** 一个用户真正关心的问题是"我这次改对了吗"，而 4322 行脚本里，能回答这个问题的只有 `gate_check`（工作树动过没）和 `verify`（测试过没过）。

**其余 4000 多行是在保证门可靠，不是保证活干得对。** 这是典型的"元工作超过本体"。

**论据三：`claim-register.md` 8 条待确认 + 6 条已撤回。**

撤回清单里有一条值得看：

> 「应给 stages 加 disable-model-invocation」→ 前提错。stages 不是独立 skill，该字段无效

**这是设计过度的证据**：曾经为了一个不存在的问题写了一条规定，后来撤回。**项目有过为想象中的场景做设计的记录。**

### 正方（主张"没有过度"）：三条

**论据一：`scope.md` 里已经写了反过度设计，且写得比反方更狠。**

原文：

> 更大的改造要写清五句：现在的做法为什么不行、大改造解决哪件具体的事、不改造的后果、更小的方案为什么不够、多出来的实现和维护成本。**说不出这五句，就用最小充分方案。**

**这是自限条款，不是过度设计。** 一个过度设计的项目不会写这个。

**论据二：这一轮我做调研时，被这套东西拦下过三次。**

- 想改 `competitive.md`，`AGENTS.md` 说"无关的债不进这次 diff" → 停住，没顺手改
- 想给 `verify.sh` 加尺寸检查，发现 N/M 没依据 → 停住（就是议题二反方那条）
- 想给 Claude Code 装 hook，判断是独立需求 → 停住，没有顺手塞

**三次都停对了。** 门确实起作用了。

**论据三：43 个用例不是浪费，是**唯一**能证明"门真的会拦"的东西。**

`claim-register.md` V6/V7 两条：

- V6：hook 拦得住 `>` `>>` `tee` `sed -i` `cp` `mv` `rm` heredoc 及 Write/Edit/multiEdit —— **实测 14 项**
- V7：hook 漏 `python -c open().write`、`git apply`、`patch`、`dd of=`、`truncate`、`install`、MCP 工具 —— **实测 5+2 项**

**V7 那条是项目自己承认漏了 7 项。** 一个过度设计的项目不会去测自己漏了哪些，只会说"我拦得住"。

### 判定：这一题双方各对一半，要分开判

| 子问题 | 判定 | 理由 |
|---|---|---|
| 门本身（6 条字面量）是不是过度 | **反方对** | 6 条里"原话 / 我理解你要的是 / 可能理解错 / 本质"是同一件事的四个说法。**写一份决定，本来就要说清这四样，拆成四个字段只增加了形式成本，没增加信息。** 这是可合并的过度 |
| 43 个用例 / 1851 行是不是过度 | **正方对** | V6/V7 证明这些用例在测"门漏在哪"，这是真需求。**但它们该被承认是"元工作"，`competitive.md` 不该把它当"活干得对"的证据** |
| 这个项目整体是不是过度 | **反方略占上风** | 4322 行脚本 / 74 个 md，服务的是"一次改动留证据"。**证据链的成本已经接近它要证明的东西的规模。** 但这是取舍，不是错误 |

**最关键的一句**：`change.md` 里"加门不是把每件事都变成问答"那段**存在本身，就是过度设计的自证**。诚实，但也是症状。

## 议题四：如果只改一处，改哪？

三方都同意的**只有一件事**：

> **`competitive.md` 那两格是事实错误，必须改。其余都可以等。**

排序（按"必须 / 可选 / 别做"）：

### 必须（1 项，2 行）

| 改什么 | 改成 |
|---|---|
| hook 降级策略那格 | 从"同类没找到（推断）"改成"官方有 `onFailure: block` 标准实现" |
| 多 agent 编排那格 | 从"差异点 ●"移到"真不如人" |

**理由**：事实错误 + 方向对自己有利 + 项目自己规定"过期要漏得响"。

### 可选（2 项，都不是现在）

| 项 | 前置条件 |
|---|---|
| `claim-register.md` 那条升格 | 无前置，但与上一项同批做，否则产生新冲突 |
| 尺寸检查 | **先量。** 量出 description 实际多少字符、在哪个宿主超了，才有 N 的依据 |

### 别做（2 项，明确否掉）

| 别做 | 理由 |
|---|---|
| 给尺寸检查拍一个 N/M | 没有依据 = 新造假确定感，违反项目自己的规矩 |
| 追 Claude Code 的 41 事件 / 4 层上下文 / subagent 隔离 | 上一轮已论证：全锚在"有运行时"，本项目第一性质是"分发 5 个宿主" |

### 加一条：**合并 `change` 的 6 条门（如果能做）**

这是本次答辩唯一一条"砍东西"的建议，来自反方最有力的攻击：

`原话 / 我理解你要的是 / 可能理解错 / 本质` 四条是**同一段思考的四个字段**。写决定的人本来就要过这四步，拆成四个 `requires` 只增加了"格式要凑齐"的成本。

**但这需要先证明"合并后还能拦住'没想就往下走'"——即一次 A/B。** 在没有那次实验前，不合并。**这条建议只登记，不执行**——否则我自己就犯了"说不出五句就用最小方案"的错。

## 判决

| 主张 | 谁赢 | 一句 |
|---|---|---|
| 该不该调 | 正方 | 该调，因为有一处事实错误，且错对自己有利 |
| 怎么调 | 反方 | 只改文档两行，不启动 `change`——为两行字走 6 道门就是过度 |
| 为什么调 | 正方 | 证据分级没覆盖"对自己的评价"，这是结构漏洞 |
| 是不是过度 | 反方略胜 | 有过度迹象（6 门可合并、4000 行元工作），但不是错误，是取舍 |
| 提升点 | 部分 | 尺寸检查**不做**，因为没有 N 的依据——反方这条赢得很干净 |

**一句话**：**这个项目已经过了"该不该有门"的阶段，现在的问题是"门比活多"。** 下一步不该加东西，该改两行错的字，然后**去量一次，而不是再写一个检查**。
