# 分析：Claude Code 这套架构，适不适合本项目

> 接 `docs/research/claude-code-architecture.md`。那篇讲"它是什么"，这篇只回答一件事：**本项目该不该往那个方向改，改哪一段，不改哪一段。**
> 判断基于本仓实际代码，不是印象。每条结论标证据。

---

## 结论先说

**大部分不适合，少部分已经在用，有一个真缺口但补不了。**

拆成四块说：

| Claude Code 的做法 | 本项目现状 | 判断 |
|---|---|---|
| 把步骤切成 41 个可挂载生命周期事件 | 只用了 **3 个**（`sessionStart`、`preToolUse`、`beforeShellExecution`），且是 Cursor 的事件名 | **不要追**。见 §2 |
| 默认 fail-open，显式开关才 strict | **已经有，同一个设计** | 已经在用，不是差距。见 §3 |
| 上下文四层分级 + 压缩后重挂预算 | 分级有（SKILL.md 选型 → 阶段文件），**预算机制没有** | **这一个是真缺口**，但补不了。见 §4 |
| subagent 三重隔离，并行靠 worktree | **没有运行时**，只能写"禁止并行" | 架构级缺口，不是改动能补的。见 §5 |

一句话：**Claude Code 的架构强在"有运行时"，本项目的价值在"没有运行时也能留下证据"。这两件事不是同一层的东西，抄不过来。**

---

## 1 先看清：本项目是什么形态

**已证实**（`scripts/install.sh:88`、`docs/install.md`）：

```
for d in .claude .cursor .qoder .codex .agents; do
```

一份源分发到 5 个工具目录。这是本项目第一个不能丢的性质。**它的存在前提就是"不绑定任何一个宿主"。**

**已证实**：本项目本体是
- 62 个 markdown（`skills/ docs/ stages/`）
- 11 个脚本（`skills/data-workflow/scripts/`）
- 3 个 hook 文件（`hooks/`），只对 Cursor 生效

**没有一个常驻进程，没有模型调用**（`claim-register.md` V5：`workflow_next.py` 零 LLM 调用）。

**这是关键**：Claude Code 的四条差异，三条都建立在"我是运行时"之上。本项目是"一组被宿主读的文件 + 几个被宿主调用的脚本"。**形态不同，架构不能平移。**

---

## 2 41 个 hook 事件：不要追

### 为什么不该追

**已证实**（`.cursor/hooks.json`）：本项目只挂三处。

```
sessionStart        → hooks/session-start
preToolUse          → hooks/gate-edit
beforeShellExecution → hooks/gate-edit
```

41 个事件里，本项目用得上的其实就三类：**会话开始**（注入 NOTICE）、**动作前**（拦写）、**动作后**（暂无）。

剩下的 38 个里，大部分依赖本项目没有的东西：

| 事件 | 用不上，因为 |
|---|---|
| `PostToolBatch` | 本项目没有并行工具调用的概念，一个 turn 一件事 |
| `PreCompact` / `PostCompact` | 压缩是宿主行为，本项目不管理上下文窗口 |
| `PreModelSwitch` | 本项目不选模型 |
| `Elicitation` | 本项目不走 MCP |
| `TeammateIdle` | 本项目禁止多 agent |
| `WorktreeCreate` | 本项目不管隔离 |

**结论：41 这个数字对本项目没有意义。** 它反映的是 Claude Code 运行时的复杂度，不是"架构先进度"。把它当标杆去追，会让 3 个 hook 膨胀成没人维护的一堆。

### 唯一值得看一眼的：`TaskCompleted`

**已证实**（`hooks.md`）：事件描述是 "When a task is being marked as completed"。

这正好是 `done` 那个动作。**推断**：如果以后要在 Claude Code 里跑本项目，`TaskCompleted` 是比 `done` 更可靠的位置——因为是宿主在"标记完成"这个瞬间调你，不是模型记得去敲 `done`。

但**当前不成立**：本项目在 Claude Code 里根本没装 hook（`install.sh` 只有 `merge_cursor_hooks`，grep `claude.*hook` 无结果）。**要做也得先有 `.claude/settings.json` 的安装分支，那是新功能，不是"追架构"。**

## 3 fail-open：已经在用，别当成差距

这一条单独说，因为它是**唯一一个本项目已经做对、且和官方设计撞上的**。

**已证实**（`hooks/gate_edit.py:9-12` 注释）：

> 2. **默认 fail-open。** 脚本出错、输入不是 JSON、解释器缺失时放行并说明。只有该项目在 config.yaml 写 `gate_strict: "true"` 时才改成拒绝。

**已证实**（Claude Code `hooks.md`）：默认 fail-open，`onFailure: "block"` 才转阻断。

**这两句是同一个设计。** 上一轮调研说"本项目差异点②：门禁有明确的失效策略，同类里没找到对应设计（推断）"——那个"推断"现在可以确认：**不是本项目独创，是官方也有标准做法。**

**这对本项目是好消息，不是坏消息**：说明这个设计是对的，不用改。但 `docs/competitive.md` 里把它当差异点讲，措辞要改。

## 4 上下文预算：真缺口，但补不了

### 缺的是什么

**已证实**（本项目）：`SKILL.md` 102 行做选型 → 阶段文件点名才读。分级有了。

**已证实**（Claude Code `skills.md`）：技能正文压缩后重挂，**每技能 5000 tokens、总计 25000**，超了从最老的丢；`description` 截断在 **1536 字符**。

**本项目没有任何等价机制。** 具体后果：

1. **阶段文件没有上限。** `stages/requirement-analysis/SKILL.md` 161 行，十来个阶段加起来 1090 行。宿主上下文满了压缩之后，**哪些还在、哪些被丢了，本项目管不着，也不知道**。
2. **`description` 没有字符预算概念。** `SKILL.md` 的 description 是一长串触发词（"开始开发、架构设计、梳理业务…"）。在 Claude Code 里这段会被截断在 1536 字符——**本项目不知道自己的 description 有没有超**。
3. **多套装一起常驻会抢同一个上限。** `docs/external-skill-packs.md` 写"三套不要同时常驻，description 会一起进上下文"——那句话现在有量化口径了，但本项目自己**没测过自己的 description 占多少**。

### 为什么补不了

**这三条都要读宿主的 token 预算，而每个宿主都不一样。** Cursor、Claude Code、Codex、Qoder 的窗口大小和压缩策略各不相同，本项目一份源要进 5 个目录，**写死哪个数字都是错的**。

**所以正确的做法不是补机制，是补一条可自查的约束**：

> 值得做的一件事：把 `SKILL.md` 的 description 长度和阶段文件行数变成 `scripts/verify.sh` 的一条检查（比如"description ≤ N 字符、单阶段 ≤ M 行"，N/M 取一个不依赖宿主的保守值）。

**这是本项目能做的**：不是去实现预算，是把"超过某个尺寸就会在某个宿主里失效"这个事实，变成一条跑得起来的检查。**成本低，且符合本项目一贯的"可验证"取向。**

**不建议做的**：去实现"压缩后重挂"。那是宿主的活，本项目做不了，假装做了就是假完成。

## 5 subagent 隔离：架构级缺口，认了

**已证实**（本项目 `SKILL.md`）："实现类禁止并行"。`docs/competitive.md` 写的理由是"同一批文件、共享工作区会互相覆盖"。

**已证实**（Claude Code `sub-agents.md`）：并行可行，靠 `isolation: worktree` 换隔离；fork 直接继承整个对话。

**判断：这不是本项目做得更严谨，是本项目没有隔离手段。**

但**补不了**，而且**不该试**：

1. 隔离要靠运行时创建 worktree、管理生命周期。本项目是脚本，能 `git worktree add`，但**没法保证 agent 真的在里头干活**——那要靠宿主强制。
2. 本项目已经用 `docs/subagent-protocol.md` 的"取证可并行、裁决不可并行"做了软约束。**这是在无运行时下能做到的最好一档。**

**该做的是把话写准**：`competitive.md` 现在把它列在"真的差异点"里（多 agent 编排纪律 ●），措辞读起来像优势。**应该改成"能力缺口 + 已知的降级做法"**，和 §1 里"知识不落仓库"一样归到"真不如人"那一栏。

---

## 6 "把计划搬进代码"：本项目已经做了，方向对

**已证实**（本项目）：`workflows/*.json` + `workflow_next.py` 算下一步，零 LLM 调用。`docs/execute` 里那句"下一步由脚本按 run.json 算"。

**已证实**（Claude Code `workflows.md`）：静态对照表里，"谁决定下一个做什么"一栏，Workflows 是**脚本**，其余三列都是模型逐 turn 决定。

**同一个思路。** 本项目在这一点上方向正确，且已经落地。

差的只是规模：Claude Code 的脚本能驱动几十到几百个 agent，本项目的脚本只算"下一步是哪一步"。**这个差距不该追**——1 个技能追并发 agent 没有意义，且违反本项目"禁止并行实现"的现有纪律。

**这格可以进 `competitive.md` 当已证实的优势**，而且是**有官方对照表背书的**优势，比自说自话强。

## 7 那到底该做什么

按"做了有用 / 做了没用"排：

### 该做（3 件，都是小改动）

| # | 改什么 | 为什么 | 成本 |
|---|---|---|---|
| 1 | `competitive.md`：hook 降级策略那格，从"同类没找到（推断）"改成"官方也有标准实现" | 现在在往对自己有利的方向写，官方文档直接反驳 | 一行 |
| 2 | `competitive.md`：多 agent 那格，从"差异点 ●"移到"真不如人" | 把没有隔离手段说成编排纪律，是虚假确定感 | 一行 |
| 3 | `verify.sh` 加一条尺寸检查：description 字符数、单阶段行数 | 唯一能真正对冲 §4 缺口的动作，且不依赖宿主 | 十几行 |

### 不该做（3 件，明确否掉）

| 不做 | 理由 |
|---|---|
| 去追 41 个 hook 事件 | 本项目 38 个用不上（§2），追了就是维护负担 |
| 去实现"压缩后重挂" | 宿主行为，本项目做不了；假装做了 = 假完成 |
| 去实现 subagent 隔离 / 并行实现 | 需要运行时强制，脚本做不到（§5） |

### 该看情况（1 件）

**给 Claude Code 装 hook**（`.claude/settings.json` 分支）。现在 5 个工具目录都能装技能，但只有 Cursor 有门禁。**这确实是能力不对等**：在 Claude Code 里用本项目，`protected_paths` 拦不住任何东西。

但这是**新功能**，不是"适合不适合"的问题，而且要先决定：`.claude` 分支用的是 Claude Code 的事件名和输入契约，和 Cursor 的 `beforeShellExecution` 不是一套。**要动就是一次独立的需求，得走 `change`，不能顺手塞。**

---

## 8 一句话回答

**不适合把本项目改造成 Claude Code 那个形状。** 它的架构价值（41 事件、四层上下文、subagent 隔离）全部锚在"有运行时"上，而本项目的第一个性质是"分发到 5 个宿主、不绑任何一个"。

**但有三条可以直接用**：fail-open 的设计（已经在用，写准就行）、"计划搬进代码"（已经在做，方向对）、尺寸要有上限（真缺口，用一条检查兜住）。

**照抄架构会把它变成一个残缺的 harness；把这三条收进来，它会变成一个知道自己边界在哪的技能包。** 后者才是它现在的位置。
