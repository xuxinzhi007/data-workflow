# 需求判断与改动定界

动手前读这一份。简单任务用几句答完。高风险任务要有 `文件:符号` 或命令输出。用户说的实现方式不是目标本身。

## 先回答

这五条用来核对。发给用户的第一份只按 `doc-shape.md` 的结论层。

- 用户真正要解决的问题是什么？怎样算这次已经满足？
- 现有代码和知识层里，哪一处已经能做？先按下面的「查证义务」把能自己查的事实查完，再给方案。没有出处的词标待确认，不编口径。
- 最小充分方案是什么？为什么更小的做法不够？
- 跟这次有关的技术债属于哪一类？无关的不进这次 diff。
- 是否碰到契约、持久化、权限、状态一致性或回滚？碰到了就不能因为「看起来很小」留在小改动流程里。

关键目标或验收说不清时，只问会影响方案选择的那一句，然后 `wait`。不影响方案的细节不清楚，写明假设后继续，不要停整次开发。

## 查证义务（给方案之前）

**能自己查的事实，在给方案前先查完。** 不许把查证当成问题反问用户，也不许用「待确认」掩盖没查。

判据不是「这事难不难」，而是「这条事实在哪」：

| 事实在哪 | 该谁查 | 做不到时 |
|---|---|---|
| 本机文件、已装软件、应用包、日志、命令输出 | **你查**。`ls` / `read` / `grep` / `strings` / 跑一遍 | 只有真的没权限或路径不存在才能说查不到 |
| 公开文档、仓库 README、依赖包的 `package.json` | **你查** | 同上 |
| 业务口径、优先级、要不要做 | **问人**。这不是事实，是决定 | 用 `wait`，写清需要谁拍板 |
| 别人机器上的状态、线上数据、未公开的内部系统 | **问人** | 同上 |

用户说「X 工具能不能做 Y」时，先分清两件事：**X 有没有这个能力**（事实，你查）和**要不要用这个能力**（决定，用户定）。把前一件反推给用户，就是把自己的活外包。

### 查不到时的输出形状

不许只说「待确认」。按这三行写：

```
卡在哪：<具体路径 / 命令 / 文档名>
缺什么：<权限 / 文件不存在 / 需要账号>
谁去补：<我能做的下一步 / 需要你提供什么>
```

「我能做的下一步」优先。只有真的只能由人做时，才写「需要你」。

### 不通过的样子

两种，都很常见：

- **把查证反推给用户**。四轮往返的全部成本都来自第 1 轮少跑三条命令：`ls` 看插件形态、`ls /Applications` 找 app、`strings app.asar` 拿 API 名。第 1 轮就能查完的，拖到第 5 轮才查。
- **把「我需要你去确认一下」写成建议**。这看上去是谦逊，实际是把自己该干的活转给用户。

## 证据

影响需求理解、方案选择、数据正确性、权限或兼容性的结论，标这四类之一。其余句子不必加标签。

| 标记 | 含义 |
|---|---|
| 已证实 | 有 `文件:符号`、测试输出，或人对业务规则的明确确认 |
| 推断 | 证据支持，但还有别的解释 |
| 待确认 | 缺关键口径。先 `wait`，不要用流畅的话补上 |
| 存在冲突 | 来源互相矛盾。写明哪几份，然后 `wait` |

代码能证明系统现在会拒绝请求，不能据此写成「业务要求永远拒绝」。那可能是缺陷，也可能是故意的约束。旧文档说必填，也不能代替当前代码和最新口径。文档和代码冲突时：当前行为回代码；业务意图问人。

先查卡片，再读相关的一个域文件，再回代码。证据指向另一个域、出现 `CONFLICT`、或这条规则明确跨域时，再读那一个，并写明原因。不要把整个知识库塞进这次上下文。

**域文件优先读仓库内的 `$DOMAIN_DOCS/<域>.md`**（`paths.sh` 解析；存在才用）。它随代码提交、能 review、能被 `knowledge_drift.sh` 判新鲜度。`$KNOW` 是补充源，引用时标「未核对」。看什么维度见 `references/business-model.md`。

## 把规则连到代码和旧决定

命中卡片后，打开它的 `watches` 和 `source_paths`，对照当前代码。在 `decision.md` 或回答里写三样：卡片 id、`文件:符号`、现在是否仍符合。

- 仍符合：标已证实，按这张卡做。
- 代码已变、卡还写着旧规则：标存在冲突。当前行为以代码为准。业务上还要不要旧规则，`wait` 问人。人确认旧规则作废后，旧卡标 `superseded`，新卡用 `supersedes` 指向它。
- 没有卡片：写「无旧决定」，只带 `文件:符号`。不要把代码里的现状写成一条没人确认过的业务规则。

## 三级

代理自己说「这是小改动」不算数。受保护路径以 `references/edit-gate.md` 和该仓库的 `protected_paths` 为准。

| 级 | 何时 | 怎么走 |
|---|---|---|
| L1 | 已有边界内的局部改动，不碰契约、持久化、权限、状态、回滚 | `change`。按 `templates/decision-template.md` 写 `decision.md`。不写 ADR，不走九步。受保护路径仍要 `passes.log`，口头定级放行不了 |
| L2 | 跨模块，或重复逻辑已经让这次改动改到无关处 | 仍先写 `decision.md`。要对比最小方案和结构性方案时，再读影响面阶段。范围停在能解决问题的那一圈 |
| L3 | 公共契约、数据迁移、权限边界、状态机、跨服务契约、难以回滚 | data-service（Go 栈）实例走 `feature` 或 `hotfix`；未声明 Go 栈的项目 L3 / 定架构走 `change`（形状写进 `decision.md`）。关键风险没写清，不写 `plan pass`，也不改受保护文件 |

## 技术债：现在还不还

碰到旧设计时选一个，写进 `decision.md`。不打分，不建台账。细则在 `stages/requirement-analysis/references/debt-gate.md`。

| 选择 | 何时 |
|---|---|
| A 现在偿还 | 它影响这次的正确性、安全或实现成本，而且修的范围可控 |
| B 局部偿还 | 只消掉这次必须碰到的那一处，其余旧结构留着 |
| C 暂缓 | 问题是真的，但和这次关系弱、风险可控。写下影响、什么时候再处理 |
| D 不能带过 | 安全漏洞、数据损坏、关键规则错误、不可接受的兼容风险。升级或请有权的人拍板，不因赶迭代默认接受 |

与这次无关的历史问题走 C，不顺手改。债也可以是规则没说清、旧决定已经不适用、多个服务对同一个词定义不一致，不只是代码难看。

## 反过度设计

已有能力能满足时，复用 `文件:符号`。不为局部需求加新抽象、中间层、配置系统、依赖或数据结构。

更大的改造要写清五句：现在的做法为什么不行、大改造解决哪件具体的事、不改造的后果、更小的方案为什么不够、多出来的实现和维护成本。说不出这五句，就用最小充分方案。

最小不是行数最少。重复已经造成业务规则不一致时，继续复制也不是更小的成本。

做完后看 diff：超出 `decision.md` 或 `spec.md` 里写的范围的，删掉或说明为什么现在就要。测试退出码是验证下界，还要对照验收条件看目标是否真的达到。
