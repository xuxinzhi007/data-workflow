# 验收标准

回答一件事：**这次改动，凭什么说它验过了。**

`exit` 和 `verify.log` 只证明"有一条命令跑完了"。它不证明那条命令验的是这次改的东西。这份文件补的就是中间那一环——把"该验什么"写成能复算的话。

写完的结论落两处：
- 项目级底线 → 被安装仓库的 `acceptance.md`（本文件是模板与规范）
- 单次增量 → `specs/<feature>/decision.md` 的「怎样算满足」与 `check.md` 的「验收结论」

## 四个必填要素

一条验收条件，缺任一要素就不算定义清楚：

| 要素 | 写什么 | 反例 |
|---|---|---|
| 命令 | 能原样粘贴执行的一条 | 「跑一下测试」 |
| 点名用例 | `TestXxx` / `TestYyy`，不是"全部" | 「全部通过」 |
| 期望关键输出 | 必须出现的那一行/那个字段/那个状态码 | 「返回正常」 |
| 覆盖哪条决策条件 | 对应 decision.md「怎样算满足」的第几条 | 不写 |

「全部通过」不合格，原因是它不可区分——分母变了也算通过，等于什么都没说。

## 判定三态，不是两态

跑完之后只有三种结论，不许含混：

| 结论 | 判据 | 能不能写进 check.md 当"通过" |
|---|---|---|
| **通过** | 点名用例全绿，关键输出对得上 | 能 |
| **失败** | 用例红了，原因指向被改的代码 | 能（如实写失败） |
| **没验成** | 环境/依赖/端口没起，用例根本没跑到被测逻辑 | **不能** |

"没验成"是最容易被写成"通过"的一种。典型样子：

```
FAIL tests/api  503 connection refused: 127.0.0.1:9004
ok   tests/e2e
```

e2e 绿了，api 因为依赖服务没起而 503。这不是"改动正确"，是"没验成"。**三个都要写，缺一个就是漏报。**

## 两层怎么写

### 项目级：定底线，一次写

落在被安装仓库的 `acceptance.md`。它回答"这个仓库永远该验什么"，不随单次改动变。

```markdown
## 底线
- 命令：make test
- 必须全绿：tests/api、tests/e2e
- 依赖前置：rbac(9004) 必须先起，未起则本次判"没验成"而非通过
- 已知不可信：tests/api 中带 sleep 的三条，偶发红，不计入判定
```

项目级底线写进 `config.yaml` 的 `verify` 之外单列，不塞进 `verify` 命令里——命令负责执行，这份文件负责判定。

### 单次改动：定增量

落在 `decision.md`「怎样算满足」，只写这次多出来的：

```markdown
## 怎样算满足（可执行）
1. 命令：go test ./tests/api -run TestTagAPI_AssociateTaskTag
   点名用例：TestTagAPI_AssociateTaskTag/success_associate_and_duplicate_error
   期望输出：200，且响应体含 tag_id
   覆盖：decision 验收条件 1
```

改动结束时，`check.md` 逐条对回来：

```markdown
## 验收结论
- exit: 0
- 验的用例：TestTagAPI_AssociateTaskTag/success_associate_and_duplicate_error
- 对应 decision 条件 1：达到
- 未覆盖：条件 3（本次不在 diff 内，见「这次不做」）
```

## 什么时候算"沉淀完了"

一条验收条件沉淀完成，要满足：**换个人、换个会话、不看聊天记录，只读 decision.md 和 acceptance.md，能独立跑出同样的结论。**

做不到这一条，说明它还是"我知道怎么验"，不是"验收标准存在"。这正好对应 Skill 的判定：能被描述清楚、能脱离当前会话复述，才算固化。

## 边界

- 这份文件不管"该不该做这个改动"，只管"做完之后怎么算验过"
- 不替代项目自己的测试入口；它约束的是**怎么读退出码**，不是**怎么跑命令**
- `exit 0` 只是通过的下界，不是充分条件。它证明命令跑完且成功，不证明验的是正确的东西
