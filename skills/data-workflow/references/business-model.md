# 业务分析的九个维度

> 这是**骨架**，不是知识库。本文件只回答"该看什么、去哪看、证据长什么样、常见的错答是什么"。任何取值（状态数字、字段名、表名、SQL 条件）都不写在这里——那些一个 commit 就会变假，且假了没有声音。
>
> 用法：`stages/oncall/references/routing.md` 定位到域之后，按这张表逐维度过一遍；`references/scope.md` 的五问先定级，这里负责"看什么"。**一次只用一个维度**，不要一次把九维全铺开——九维同时加载会让结论互相污染（同 `state-protocol.md` 的一族一上下文）。
>
> 每个维度的结论都要带四态之一：`已证实` / `推断` / `待确认` / `存在冲突`（定义在 `scope.md`）。

---

## 1 对象与身份

**问什么**：这个业务里被操作的东西是什么？主键是什么？谁创建它，它活多久？

**去哪读**：数据模型（表/列）、领域结构体、创建入口。

**证据形式**：`文件:符号` + 主键字段名（不含取值）。

**典型错答**：把接口 DTO 当领域对象；把展示名当身份；把"表里有一行"当成"业务上存在一个对象"。

## 2 状态族

**问什么**：这个实体有几套**正交**的状态？各自权威定义在哪？

**去哪读**：见 `state-protocol.md`。它只有流程没有取值表，取值一律现场读。

**证据形式**：`族名(列)` 的限定写法 + 权威 const 块位置。

**典型错答**：把 Proto 枚举当完整状态目录；按数值大小推生命周期；两族同名数字横向比较。

## 3 迁移与守卫

**问什么**：谁能把 A 改成 B？前置条件是什么？失败会留下什么？

**去哪读**：全部写入口（不只主流程），以及它们前面的 guard。

**证据形式**：写入口 `文件:符号` + 守卫函数名 + 事务/CAS 边界。

**典型错答**：从读侧推断写规则；只找到一条写入口就当作唯一入口；把"现在拒绝"读成"业务要求永远拒绝"（按 `scope.md`：代码证明当前行为，业务意图问人）。

## 4 读侧可见性

**问什么**：值写进去了，用户为什么还看不见？

**去哪读**：列表/详情查询入口，而不是写入链路。

**证据形式**：可见性过滤的 `文件:符号`（租户/范围/软删/关联表/分页/派生筛选）。

**典型错答**：把"落库成功"当"用户可见"；只看状态过滤，漏掉租户与数据范围。

## 5 角色与数据范围

**问什么**：有哪些角色？各能做什么？越权边界在哪一层拦？

**去哪读**：鉴权中间件 + 资源归属校验（不是路由表）。

**证据形式**：中间件名 + 归属校验函数名；缺哪个角色的覆盖要显式写"未覆盖"。

**典型错答**：把"接口有鉴权注解"当成"资源归属已校验"；把菜单权限当数据权限。

## 6 外部通道

**问什么**：这件事有没有主动推送、回调、定时任务、消息队列？契约在哪？

**去哪读**：搜 topic / scheduler / webhook / 客户端名字，**不要先信文档说"没有"**。

**证据形式**：发送点 `文件:符号` + 接收方 + 有没有单测。

**典型错答**：仓库 `docs/` 说"服务内没有 MQTT"就当成事实（本仓 `knowledge-sources.md` 记录过同类假话）；只看自己服务，不看调度器和外部回调。

## 7 幂等与重试

**问什么**：同一次请求重放一次会怎样？靠什么挡住？

**去哪读**：写入口的事务边界、唯一键、CAS、去重表。

**证据形式**：挡住重复的具体机制 `文件:符号`；没有就说没有。

**典型错答**：假定 HTTP 重试幂等；把"前端只发一次"当约束。

## 8 审计与通知

**问什么**：这件事发生之后，谁需要知道？发送失败怎么补？

**去哪读**：通知/事件/日志的发送点，以及失败兜底。

**证据形式**：发送点 + 失败路径（重试队列 / 补偿任务 / 只记日志）。

**典型错答**：把日志当通知；只看发送成功路径。

## 9 契约

**问什么**：对外暴露了什么（字段、错误码、兼容性）？谁是调用方？

**去哪读**：该项目的契约事实源（proto / openapi / 类型定义）+ 调用方。

**证据形式**：字段 + 语义 + 调用方清单；改语义要单列为 breaking。

**典型错答**：把契约文件当业务事实源（它只描述传输，不描述规则）；把"前端在用"当成"契约稳定"。

## 收尾：一次分析的产出形状

按 `references/doc-shape.md` 的结论层给，不铺九维全文：

```
结论    要不要改 / 现在能不能改 / 下一步
依据    命中哪几个维度、各自的 文件:符号、哪些标了待确认
产出    仓库内域文档（templates/domain-doc-template.md）或一张卡片
```

**写在哪**（优先顺序，`paths.sh` 的 `$DOMAIN_DOCS` 就是第一项）：

| 落点 | 进 git | 谁写 | 适合放什么 |
|---|---|---|---|
| `$REPO/docs/domain/<域>.md` | 是 | 人确认后 agent 写 | 团队共识：对象、状态族名、写入口、可见性、角色范围。**不写取值。** |
| `$REPO/GLOSSARY.md` | 是 | 人 | 术语：这个词在本业务里指什么 |
| `$CARDS/` | 否 | agent | 个人调查线索、一次事件的现象与证据 |
| `$KNOW/**` | 视知识库而定 | 人 | 补充源。引用时必须标「未核对」 |

**当仓库内与 `$KNOW` 冲突时，以仓库内 + 代码为准**，并在结论里点名冲突在哪。理由是仓库内的那份随代码提交、能被 review、能被 `knowledge_drift.sh` 判新鲜度。
