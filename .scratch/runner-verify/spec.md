# 编码结束要有一条仓库自己的检查

## Problem Statement

代理用很长的说明代替正在做的那一步，并在没有跑过会失败的命令时宣布编码结束。页面和模型路由不解决这件事。把检查写成某一个服务的测试命令，换一个仓库就失效。

## Solution

两层。底层是任意仓库都能用的运行记录和写入门禁。上层是那个仓库自己的阶段和配置。编码步骤结束时，跑该仓库声明的测试入口。没有声明，或退出码不是 0，就停住。使用者自己执行安装。技能仓库的开发不改消费仓库的配置。没有未完成的运行时，会话不注入用法说明。

## User Stories

1. 作为新开会话的代理，我希望没有未完成的运行时上下文是空的，以便回答当前问题。
2. 作为接手未完成运行的代理，我希望只看到下一步，以便不重读已完成阶段。
3. 作为回复过拍板的人，我希望回复被记下来，以便下一轮不用再问。
4. 作为回到已完成运行的代理，我希望只看到运行名和记录路径，以便不把用法说明再读一遍。
5. 作为结束编码步骤的代理，我希望先跑仓库声明的检查，以便不能空口说做完了。
6. 作为检查失败的代理，我希望步骤不前进，以便红的结果停住。
7. 作为 npm、pnpm 或 yarn 仓库，我希望用它自己的 test 脚本，以便不用另写命令。
8. 作为有 Makefile test 目标的仓库，我希望跑 make test。
9. 作为 pytest 仓库，我希望跑 pytest。
10. 作为 Cargo 仓库，我希望跑 cargo test。
11. 作为写了 verify 的仓库，我希望这条命令优先，即使它失败。
12. 作为只有 go.mod、没有声明检查的仓库，我希望停住，以便不被猜一条测试命令。
13. 作为 data-service 的开发者，我希望写入门禁还在。
14. 作为 data-service 的开发者，我希望原有阶段链还在。
15. 作为其他仓库的开发者，我希望同一套「下一步 / 退出码」循环可用。
16. 作为技能作者，我希望只改技能仓库。
17. 作为使用者，我希望自己运行安装把副本同步过去。
18. 作为已安装其他技能的人，我希望那些技能还在。

## Implementation Decisions

- 底层是运行记录、下一步和写入门禁。阶段正文留在各仓库的工作流里。
- 不做页面，不做模型路由。
- 会话只在有未完成运行时注入下一步。
- 检查命令的顺序：配置 verify，package.json 的 test，Makefile 的 test，pytest，cargo test。都没有就停。
- 显式 verify 优先，即使非零。
- 日志记下退出码和输出。非零不前进。
- 技能开发不改消费仓库配置。
- 对外只有一个检查入口：编码步骤的 done。

## Testing Decisions

只测外部行为，用临时仓库。覆盖：没有检查入口、package.json 的 test、Makefile 的 test、只有 go.mod、显式 verify 覆盖 package.json 且命令失败。

## Out of Scope

- 可视化页面
- 接入豆包或任何模型路由
- 把七段阶段收成一份空模板
- 并行实现者和 worktree
- 开发技能时修改 data-service
- 替换机器上已有的其他技能
- 按语言猜一条默认测试命令

## Further Notes

本机 `config.yaml` 被 gitignore。里面的 verify 不随仓库发布。

别的仓库用安装后的副本。那个仓库里的代理读副本的 `SKILL.md`：有未完成运行就按 `next` 做一件事，编码结束跑该仓库自己的测试入口。检查命令包含一次装进临时仓库的全路径。
